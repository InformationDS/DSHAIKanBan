# AIKanBan MVP 产品需求文档

## 1. 文档定位

### 1.1 文档目的

本文档定义 AIKanBan MVP 的产品问题、目标用户、产品目标、范围、核心概念、用户旅程、功能行为、验收标准、风险与待决问题。

本文档是 MVP 产品需求的主要事实来源。后续产品需求发生变化时，应在本文档中更新并保留必要的决策背景，不再创建内容重复的 PRODUCT.md。

### 1.2 文档边界

本文档描述用户可见的产品行为和验收结果，不详细设计以下内容：

- 具体框架和依赖
- 数据库字段、索引和 migration
- API 路由和通信协议
- 代码目录结构
- 类、接口和模块实现
- 详细技术架构
- 凭据存储和加密算法

上述内容应分别在后续 ARCHITECTURE.md、DATA_MODEL.md 或专项技术设计中维护。

### 1.3 当前状态

- 文档状态：MVP 产品需求已确认
- 产品形态：运行在用户本机，通过 localhost 浏览器使用
- 目标发布阶段：MVP
- 主要验证方式：使用 AIKanBan 管理 AIKanBan 自身开发

## 2. 产品背景与问题陈述

### 2.1 产品背景

个人开发者越来越多地使用 Codex 参与功能开发、缺陷修复、调研、重构和文档工作。一个真实开发任务通常无法在一条对话中完成：任务可能因上下文长度、阶段切换、工作中断或探索不同方案而分布在多条独立对话中。

现有对话历史能够保留单次交流，却不能自然形成一份由用户确认、适合交给下一条对话继续使用的任务状态。普通工作项工具又通常不知道 AI 对话中已经作出的决策、完成的工作、验证结果和未解决问题。

AIKanBan 将项目、工作项、Codex 对话和可审核的记忆连接起来，使跨对话开发工作具备连续性。

### 2.2 核心问题

当一个开发任务跨越多条独立 Codex 对话时，个人开发者缺少一个可信、可控的交接机制，因此容易出现：

- 新对话不了解任务目标、范围和重要约束。
- 已确认决策被遗漏、误解或重复讨论。
- 已完成工作和验证结果难以快速恢复。
- 未解决问题、阻塞原因和下一步丢失。
- 自动摘要未经审核，可能把错误推断带入后续对话。
- 用户需要反复阅读、复制或重新解释旧对话。
- 项目级共识散落在多个工作项和对话中，无法稳定复用。

### 2.3 产品机会

AIKanBan 不把“自动总结对话”当作最终结果，而是建立一条用户可控制的可信链：

1. Codex 根据对话和当前已确认记忆提出更新建议。
2. 用户查看差异、修改内容并明确确认。
3. 只有已确认内容才成为后续对话的交接上下文。
4. 每次变化都能追溯到基础版本和来源对话。

### 2.4 当前证据与限制

MVP 的问题判断主要来自产品发起者自身使用 Codex 进行软件开发的实际需求，尚无外部用户研究、市场规模或留存数据。MVP 首先通过真实自用验证问题和闭环是否成立，不把未经验证的广泛市场假设写成既定事实。

Codex App Server 最小技术实验已经验证：由 AIKanBan 创建、关联并由其所属 App Server 管理的 thread 可以支撑创建、运行、流式查看、读取已完成历史、继续和停止等核心闭环。实验同时证明，既有历史发现、跨进程全局状态和后端或 App Server 退出后的活动 turn 恢复不能作为首版已确认能力。MVP 的 Codex 工作区必须遵守这些边界。

## 3. 目标用户与典型场景

### 3.1 主要用户

MVP 只聚焦一种主要用户：

> 在本机使用 Codex 完成软件开发工作，并经常需要让同一任务跨越多条独立对话的个人开发者。

### 3.2 用户特征

- 同时维护一个或多个本地代码项目。
- 使用 Codex 处理功能开发、缺陷修复、重构、调研或文档任务。
- 对话可能因中断、上下文长度或探索方向而拆分。
- 希望保留经过自己确认的目标、决策、进展和下一步。
- 重视本地数据控制以及发送给 AI 的上下文透明性。
- 愿意审核记忆差异，而不是完全依赖自动总结。

### 3.3 用户待完成任务

当开发工作跨越多条 Codex 对话时，用户希望能够：

- 快速看清一个工作项当前可信的状态。
- 在新对话中继续任务，而不必重新阅读或复制旧对话全文。
- 控制 AI 对任务事实的增删和改写。
- 知道一条记忆何时、基于哪条对话和哪个版本产生。
- 把多个任务中形成的长期共识提升为项目级上下文。

### 3.4 典型场景

- 一个功能跨多次 Codex 对话逐步完成。
- 调试过程中开启新对话验证不同思路。
- 中断数天后重新继续工作项。
- Codex 工作区不可用时，生成已确认上下文并复制到官方 Codex 客户端继续工作。
- 从多个工作项中提炼项目级决策与约束。
- 使用 AIKanBan 管理 AIKanBan 自身开发。

### 3.5 不单独服务的用户

MVP 不为以下用户群单独优化：

- 软件团队负责人或项目经理
- 非技术个人任务管理用户
- 需要远程或移动访问的用户
- 需要多人共享状态的团队
- 需要多个 AI 提供方统一管理的用户

## 4. 产品目标与成功标准

### 4.1 产品目标

1. 让一个开发工作项能够跨多条独立 Codex 对话连续推进。
2. 让用户而不是 AI 决定哪些内容成为正式记忆。
3. 让项目级和任务级上下文各有明确范围，避免混杂。
4. 让记忆变化可查看、可编辑、可确认、可追溯。
5. 让用户在本机统一管理项目、工作项和必要的 Codex 对话操作。
6. 让产品能够管理其自身 MVP 的开发过程。

### 4.2 核心产品结果

用户能够在不重新阅读或复制前一条对话全文的情况下，使用已确认任务记忆开始一条独立的新对话，并正确继续原工作项。

新对话应能够从已提供的上下文中理解：

- 当前任务目标和范围
- 已确认决策与约束
- 已完成工作和验证结果
- 未解决问题与风险
- 下一步行动

### 4.3 MVP 自我使用验证

在宣布 MVP 达标前，使用 AIKanBan 管理其自身开发，并至少完成：

- 3 个真实工作项。
- 每个工作项至少跨越 2 条由 AIKanBan 创建和管理的独立 Codex 对话。
- 完成至少 1 次任务记忆的生成、编辑和确认。
- 完成至少 1 次基于多个工作项的项目记忆更新。
- 验证至少 1 次过期建议处理。
- 验证至少 1 次目录失效后的恢复流程。
- 验证至少 1 次 Codex 工作区启动失败关闭和“生成上下文并复制”降级流程。
- 验证至少 1 次浏览器断线但后端和 App Server 仍存活时的恢复与状态核对。
- 验证至少 1 次后端或 App Server 退出后，活动对话进入“需要重新核对”的流程。

### 4.4 质量护栏

- 未确认或已过期的记忆不得作为正式记忆发送。
- 用户能够看到每次记忆变化及其版本级来源。
- 应用重启后，已确认记忆、版本历史和对话关联仍然存在；该承诺不包含异常退出时活动 turn 的继续执行或恢复。
- 失败或重试不得产生重复版本或覆盖已确认内容。
- 产品不得删除或修改关联代码目录。
- 删除本地管理数据时，不得声称已经删除 Codex 一侧的原始对话。
- 没有项目记忆或任务记忆时，核心流程仍可继续并清楚提示空状态。

### 4.5 暂不使用的成功指标

MVP 不以活跃用户数、团队席位、留存率或云端使用量作为成功标准。产品首先验证单用户真实开发场景中的任务连续性和用户控制能力。

## 5. 产品原则

### 5.1 用户确认优先

AI 生成的内容永远是建议。用户必须能够查看差异、修改并明确确认，建议才能成为正式记忆。

### 5.2 已确认记忆才是交接事实

原始对话、生成中内容、待审核建议和已过期建议都不能被当作正式记忆自动提供给后续对话。

### 5.3 上下文透明

在向新对话或已有对话发送长期上下文前，用户应能看到将要发送的项目记忆、任务记忆和相关工作项信息。

### 5.4 项目级与任务级信息分离

项目记忆保存跨工作项、长期有效的信息；任务记忆保存单个工作项的交接状态。具体任务进度不得为了方便而无差别提升到项目记忆。

### 5.5 本机优先但不虚假承诺完全离线

AIKanBan 的管理数据保存在本机，但与 Codex 交互的内容可能离开本机。产品必须清楚区分两者。

### 5.6 保守处理不可逆操作

归档优先于永久删除。任何永久删除必须明确影响范围，且不得波及用户代码目录或虚假承诺删除外部数据。

### 5.7 控制 MVP 范围

只实现完成跨对话任务闭环所需的能力，不扩展为团队项目管理平台、通用 IDE、多 Agent 编排器或多模型客户端。

## 6. MVP 范围

MVP 包含：

- 创建、查看、编辑、归档和删除项目。
- 为项目关联一个本地代码目录，并处理目录失效和重新关联。
- 创建、查看、编辑、改变状态、归档和删除工作项。
- 在 localhost 浏览器中创建、关联、查看、继续和停止由 AIKanBan 所属 App Server 管理的 Codex thread。
- 处理 AIKanBan 所属 App Server 实际发出的审批请求。
- 在工作项之间重新关联由 AIKanBan 创建的普通任务对话。
- 查看对话所使用的项目记忆和任务记忆版本状态。
- 向已有对话手动发送最新已确认上下文。
- 在 Codex 工作区不可用时，继续管理项目、工作项和记忆，并生成可复制到官方 Codex 客户端的上下文。
- 手动生成、审核、修改、确认或放弃任务记忆建议。
- 手动编辑并版本化任务记忆。
- 手动编辑并版本化项目记忆。
- 通过项目级专用维护对话讨论并生成项目记忆建议。
- 管理记忆建议的生成中、待审核、已过期、已确认和已放弃状态。
- 查看版本级差异和来源。
- 处理空状态、错误状态、重试和恢复。
- 在本机持久保存产品管理数据。

## 7. 明确非目标

MVP 不包含：

- 多用户与团队协作
- 云同步和远程部署
- 手机端
- 多 Agent 编排
- 同时支持多个 AI 提供方
- AIKanBan 自身的插件系统
- 向量数据库和复杂 RAG
- Tauri 桌面封装
- 自动 Git worktree
- 企业权限系统
- 自动合并冲突记忆
- 自动生成或自动确认记忆
- 自动扫描整个项目生成记忆
- 复刻 Codex 客户端的全部高级功能
- 通用终端或完整 IDE 能力
- 自动调度多条对话
- 修改、注入或依赖 Codex 客户端未公开内部接口
- 发现、导入或接管既有及外部 Codex thread
- 判断其他 Codex 客户端或 App Server 是否正在运行同一 thread
- 为单条对话选择项目目录下的任意子目录作为工作目录
- 自动发现项目目录任意子目录中的历史对话
- 保证后端或 App Server 退出后活动 turn 继续或可恢复
- 接管其他 Codex 客户端已经挂起的审批
- 项目记忆与仓库文档的自动同步
- 逐句或逐消息的记忆引用
- AIKanBan 云账号、云备份或产品遥测

## 8. 核心概念及产品含义

### 8.1 项目

项目是工作项、项目记忆和相关 Codex 对话的长期容器。每个未归档项目关联一个用户明确选择的本地代码目录。

### 8.2 本地代码目录

本地代码目录定义项目中 Codex 对话的工作范围。首版中，由 AIKanBan 创建的 thread 只使用项目明确指定的这个目录，不为单条对话选择或自动发现任意子目录。AIKanBan 只记录关联关系，不因创建、更换或删除项目而移动、复制、修改或删除目录内容。

### 8.3 工作项

工作项表示一个有明确目标、状态、当前进展和下一步的开发任务。一个工作项可以关联多条相互独立的普通 Codex 对话，并拥有一条版本化任务记忆链。

### 8.4 AIKanBan 管理的普通任务对话

普通任务对话是由 AIKanBan 创建、关联，并由 AIKanBan 当前所属 App Server 管理的 Codex thread。它围绕一个工作项进行，同一时间只能关联一个工作项。首版不发现、导入或接管既有及外部 thread。

### 8.5 项目记忆维护对话

项目记忆维护对话是由 AIKanBan 创建和管理的项目级 Codex thread。它属于项目但不属于任何工作项，专门用于讨论并生成一次项目记忆更新建议。它可以选择零个或多个来源工作项，并且一条维护对话只对应一个更新周期。

### 8.6 任务记忆

任务记忆是一个工作项跨对话使用的、由用户确认的交接上下文。它不是完整对话摘要，也不是工作日志全文。

任务记忆包含六个固定分区：

1. 任务目标与范围
2. 已确认的决策与约束
3. 已完成工作与当前进展
4. 关键产物与验证结果
5. 未解决问题、阻塞与风险
6. 下一步

### 8.7 项目记忆

项目记忆是项目内所有工作项和对话可参考的、由用户确认的共享上下文。它不取代 PRD、架构文档或仓库中的其他事实文档。

项目记忆包含五个固定分区：

1. 项目目的与范围
2. 共享约束与工作约定
3. 已确认的项目级决策
4. 跨工作项上下文与依赖
5. 项目级未决问题与风险

### 8.8 记忆建议

记忆建议是 Codex 根据一条对话、当前已确认记忆和允许的来源提出的候选变化。它在用户确认前不属于正式记忆。

### 8.9 已确认版本

已确认版本是用户审核后形成的不可变记忆快照。修改已确认内容必须基于当前版本产生新版本，不得原地覆盖历史。

### 8.10 上下文版本状态

上下文版本状态表示一条对话最近一次已知收到的项目记忆和任务记忆版本。状态可以是最新、已过期或未知。

### 8.11 Codex 工作区可用性

Codex 工作区表示 AIKanBan 在浏览器内创建和驱动 Codex thread 的能力。只有 Codex CLI、兼容版本和 schema、App Server 握手以及当前运行上下文中的认证检查全部通过时，工作区才可用。任一检查失败时，工作区失败关闭，但项目、工作项、记忆、版本和归档管理继续可用。

### 8.12 对话运行状态

对话运行状态只表示 AIKanBan 所属 App Server 当前能够确认的状态，不代表机器、账户或其他 Codex 客户端范围内的全局状态。无法可靠核对时，内部状态为 unknown，用户界面显示“需要重新核对”。该状态与“上下文版本未知”含义不同。

## 9. 核心对象关系

- 一个项目关联一个当前本地代码目录。
- 一个项目拥有零个或多个工作项。
- 一个项目拥有零个或多个项目记忆版本。
- 一个项目拥有零个或多个项目记忆维护对话。
- 一个工作项只属于一个项目。
- 一个工作项拥有零个或多个由 AIKanBan 创建和管理的普通任务对话。
- 一个工作项拥有零个或多个任务记忆版本。
- 一条普通对话同一时间只关联一个工作项。
- 一条项目记忆维护对话属于一个项目且不属于工作项。
- 项目内所有 AIKanBan 管理的 thread 使用该项目当前明确指定的目录。
- 项目记忆对项目内工作项共享，任务记忆只属于单个工作项。
- 在工作项之间重新关联 AIKanBan 管理的普通对话不会移动任务记忆，也不会改写过去版本中的来源记录。

## 10. 核心用户旅程

### 10.1 创建项目并建立基础项目记忆

1. 用户输入项目名称并选择本地代码目录。
2. 系统验证目录存在且当前可访问。
3. 项目创建成功，项目记忆显示为空。
4. 用户可以直接手动创建项目记忆 V1。
5. Codex 工作区可用时，用户也可以创建一条不选择来源工作项的项目记忆维护对话。
6. 用户与 Codex 讨论项目背景、目的、范围和约束。
7. 用户手动触发项目记忆建议生成。
8. 用户查看差异、编辑并确认，形成项目记忆 V1。

### 10.2 创建工作项并开始第一次对话

1. 用户在项目下创建工作项，填写标题和目标。
2. 状态默认为未开始；当前进度和下一步可以为空。
3. 创建工作项时不自动生成任务记忆。
4. Codex 工作区可用时，用户创建由 AIKanBan 管理的普通 Codex 对话。
5. 发送前，系统展示项目目录、最新项目记忆、工作项信息、任务记忆空状态和本次补充说明。
6. 用户确认后开始对话。
7. Codex 工作区不可用时，用户可以使用同一份上下文预览并复制到官方 Codex 客户端，但不会在 AIKanBan 中创建或关联 thread。

### 10.3 生成并确认第一版任务记忆

1. 用户在普通任务对话中推进工作。
2. 用户手动触发生成任务记忆建议。
3. 系统以空白任务记忆为基础，并向 Codex 提供当前工作项信息和当前已确认上下文。
4. Codex 返回固定分区的建议。
5. 用户查看相对于空白基础的差异并进行修改。
6. 用户同时查看与工作项目标、状态、当前进度、下一步或阻塞原因相关的字段建议。
7. 用户确认后形成任务记忆 V1。

### 10.4 开启后续对话继续任务

1. 用户从工作项创建另一条由 AIKanBan 管理的独立对话。
2. 系统展示将要发送的最新项目记忆、工作项信息和最新任务记忆。
3. 用户可以添加只用于本次对话的补充说明。
4. 用户确认后发送上下文并开始对话。
5. 本次补充说明不改变正式记忆。

### 10.5 Codex 工作区不可用时复制上下文

1. Codex 工作区启动检查失败或当前不可用。
2. 项目、工作项、记忆和版本历史仍可正常查看与编辑。
3. 用户从工作项选择“生成对话上下文”。
4. 系统按照新建对话的相同规则生成上下文预览。
5. 用户可以添加或编辑只用于本次使用的一次性补充说明。
6. 用户复制完整上下文并粘贴到官方 Codex 客户端。
7. 该操作不创建或关联 thread，不跟踪外部运行状态，也不自动获取官方 Codex 客户端中的回复。
8. 用户随后可以通过手动记忆编辑维护任务连续性。

### 10.6 从多条对话更新任务记忆

1. 多条普通对话可以分别基于当前任务记忆版本生成建议。
2. 用户审核并确认其中一份建议，产生新的任务记忆版本。
3. 其他基于旧版本的待审核建议立即变为已过期。
4. 用户可以放弃过期建议，或基于最新版本重新生成。
5. MVP 不自动合并建议，也不自动解决冲突。

### 10.7 从多个工作项更新项目记忆

1. 用户从项目记忆页面创建新的项目记忆维护对话。
2. 用户选择零个或多个来源工作项。
3. 系统固定当前项目记忆版本，以及各来源工作项当时的目标、状态和最新已确认任务记忆版本。
4. 系统不读取待审核建议、过期建议、历史任务记忆版本或工作项全部原始对话。
5. 用户与 Codex 讨论哪些内容具有长期、跨工作项价值。
6. 用户手动触发项目记忆建议生成。
7. 用户查看差异、编辑并确认，形成新的项目记忆版本。
8. 本次更新确认或放弃后，该维护对话的更新周期结束。

### 10.8 处理浏览器断线或后端退出

1. 仅浏览器断线而后端和 App Server 仍存活时，后端继续维护 AIKanBan 自有状态缓存。
2. 浏览器重连后先恢复最近已知状态，再向 Codex 核对已持久化历史和当前可见状态。
3. 如果无法核对，界面显示“需要重新核对”，不得显示为已完成。
4. AIKanBan 后端或 App Server 退出时，不保证活动 turn 继续或可恢复。
5. 重启后保留项目、工作项、记忆、版本和 thread 关联；异常退出时的活动对话进入“需要重新核对”。
6. 用户完成重新核对后才能继续驱动该对话。

### 10.9 处理目录失效

1. 产品发现项目目录不存在或不可访问。
2. 项目显示目录不可用状态和原路径。
3. 用户仍可查看和编辑工作项、记忆及历史关联。
4. 在恢复或重新关联目录前，用户不能从该项目创建新的普通 Codex 对话。
5. 用户选择新的有效目录并确认。
6. 新目录只影响此后创建的对话，不改写历史对话所使用的目录。

### 10.10 归档和永久删除

1. 用户可以归档项目或工作项，使其退出活动视图。
2. 用户可以从归档视图恢复对象，原有状态和历史保持不变。
3. 永久删除只能从已归档对象发起。
4. 系统展示将删除的本地管理数据以及不会删除的代码目录和 Codex 原始对话。
5. 用户进行二次确认后，系统执行永久删除。

## 11. 功能行为规则

### 11.1 项目

- 创建项目时，项目名称和本地代码目录必填。
- 项目不再设置与项目记忆重复的项目描述或项目目标字段。
- 创建项目时不调用 Codex，也不自动生成项目记忆。
- 同一个规范化目录不能同时关联两个未归档项目。
- 允许选择另一个项目目录内部的子目录，但必须提示目录嵌套并由用户确认。
- 将某个子目录直接设置为项目目录，不代表其父项目自动包含该子目录中的 thread；每个项目只使用自己明确指定的目录。
- 创建项目不会修改所选目录内容。

### 11.2 本地目录

- 目录必须在创建或重新关联时存在且可访问。
- 产品不得自动扫描磁盘猜测目录的新位置。
- 目录失效不得导致项目、工作项、记忆或对话关联被删除。
- 目录不可用时禁止创建新的普通任务对话，但允许查看和编辑管理数据。
- 更换目录前应明确提示新目录只用于后续对话。
- 更换目录不得移动、复制或删除旧目录中的文件。
- 项目历史应能够反映目录关联发生过变化，但不记录目录内容。
- 由 AIKanBan 为项目创建的 thread 必须使用该项目当前明确指定的目录。
- MVP 不为单条 thread 选择项目目录下的其他子目录，也不自动扫描或发现任意子目录中的历史。

### 11.3 工作项

创建工作项时：

- 标题必填。
- 目标必填。
- 状态默认为未开始。
- 当前进度选填。
- 下一步选填。
- 当状态为已阻塞时，阻塞原因必填。
- 项目和目录从所属项目继承。
- 不自动创建任务记忆版本。

工作项使用以下固定状态：

- 未开始
- 进行中
- 已阻塞
- 已完成
- 已取消

状态行为：

- 状态由用户最终决定，不得由 AI 自动改变。
- 记忆建议可以提出状态变化，但必须单独展示并由用户确认。
- 已完成、已取消或已阻塞的工作项可以重新设为进行中。
- 已完成和已取消的工作项仍可查看全部对话与记忆历史。
- MVP 不支持自定义状态和自定义工作流。

### 11.4 Codex 对话工作区

Codex 工作区可用时，localhost 浏览器是 MVP 中进行 Codex 对话的主要界面。工作区只对由 AIKanBan 创建并由其所属 App Server 管理的 thread 提供以下能力：

- 创建并打开对话。
- 查看按时间排列的消息和必要的运行事件。
- 输入并发送提示。
- 查看正在运行、已完成、已停止、失败、等待确认或需要重新核对。
- 请求停止当前运行，并区分正在停止和已经停止。
- 处理 AIKanBan 所属 App Server 实际发出的命令、文件变更或其他受支持审批请求。
- 稍后继续同一条对话。
- 执行发送最新上下文。
- 手动触发任务记忆建议生成。

对话状态只表示当前 AIKanBan 所属 App Server 可以确认的运行，不代表其他 Codex 客户端或进程的全局状态。只有收到实际审批请求时才能显示等待确认，审批操作必须绑定到准确的请求和对话。用户请求停止后，只有收到最终停止结果才能显示已停止。

Codex 工作区不可用时，以上 Codex 操作失败关闭；项目、工作项和记忆管理仍然可用，并提供“生成上下文并复制”入口。

MVP 不要求复刻 Codex 官方客户端的全部设置、高级功能或通用开发环境。

### 11.5 普通对话的归属与重新关联

- 由 AIKanBan 创建的普通 Codex 对话同一时间只能关联一个工作项。
- 已关联一个工作项的对话不得同时关联另一个工作项。
- 用户可以通过明确的重新关联流程把 AIKanBan 管理的对话移动到另一工作项。
- 重新关联不得转移任务记忆或工作项字段。
- 原工作项已确认记忆版本中的来源记录继续保留。
- 原工作项中由该对话生成且尚未确认的活动建议必须先放弃，或在重新关联确认时明确作废。
- 重新关联不得复制、修改或删除 Codex 原始对话。
- MVP 不提供既有或外部 Codex thread 的发现、导入和重新关联。

### 11.6 Codex 工作区启动与降级

- Codex 工作区只有在受支持的 Codex CLI、版本和 schema 兼容性、App Server 握手以及当前运行上下文中的认证检查全部通过后才可用。
- 任一启动检查失败时，工作区必须失败关闭，不得以解析 Codex 内部 session、状态数据库或认证文件作为降级替代。
- 错误界面必须区分 CLI 不可用、版本或 schema 不兼容、握手失败和认证不可用，并提供针对性的修复指引。
- 当 Codex CLI 可以启动但 AIKanBan 当前运行上下文无法访问认证时，必须明确显示这一差异，不得笼统显示为网络错误。
- 工作区不可用不影响项目、工作项、记忆、版本、归档和删除等本地管理功能。
- 工作区不可用时，用户可以生成与新建对话相同的上下文预览并复制到官方 Codex 客户端。
- 复制操作不创建或关联 thread，不跟踪外部运行状态，也不自动获取外部回复。

### 11.7 新对话上下文

创建普通任务对话前，预览默认包含：

- 项目名称和关联目录
- 最新已确认项目记忆；如果不存在则显示明确空状态
- 工作项目标、状态、当前进度、下一步和适用的阻塞原因
- 最新已确认任务记忆；如果不存在则显示明确空状态
- 用户为本次对话添加的一次性补充说明

规则：

- 用户必须能够在发送前看到长期上下文。
- 用户可以编辑一次性补充说明。
- 用户不得在一次性上下文预览中悄悄改写正式记忆。
- 修改正式记忆必须进入手动编辑或建议审核流程。
- 新对话默认使用最新已确认版本，不允许把待审核或已过期建议当作正式上下文。
- 同一上下文组装规则同时用于 Codex 工作区不可用时的“生成上下文并复制”流程。

### 11.8 已有 AIKanBan 管理对话的上下文更新

- 项目记忆或任务记忆更新后，不自动向已有对话推送内容。
- 产品记录每条对话最近一次已知收到的项目记忆和任务记忆版本。
- 如果存在更新，对话显示上下文已过期。
- 用户可以选择发送最新上下文，并在发送前查看预览。
- 发送最新上下文不会生成建议，也不会修改正式记忆。
- 项目记忆维护对话在创建时固定来源，不允许通过发送最新上下文改变本次更新周期。

### 11.9 任务记忆

- 任务记忆属于单个工作项。
- 分区固定，分区内允许自由文本。
- 空分区可以显示暂无，不得为了填满而生成无依据内容。
- 任务记忆应简明表达交接所需事实，不保存完整对话摘要、完整日志或大段代码。
- 生成建议时应保留仍然有效的现有内容，只建议确有变化的增加、修改或删除。
- 删除内容必须在差异中清楚显示。
- 用户可以不经过 Codex 直接手动编辑任务记忆。

### 11.10 任务记忆建议生成

- 生成只能由用户手动触发。
- 创建或重新关联对话本身不触发生成。
- 生成时，系统向对话明确提供当前工作项信息和最新已确认任务记忆版本。
- 如果没有已确认任务记忆，则以空白固定分区为基础。
- 同一条普通任务对话在同一时间最多有一份活动建议。
- 一份建议被确认或放弃后，同一条任务对话可以再次生成新建议。
- 一个工作项可以同时存在来自不同对话的多份待审核建议。

### 11.11 项目记忆

- 项目记忆属于项目，供项目内所有工作项和对话参考。
- 项目记忆不跨项目共享。
- 项目记忆不取代 PRD、ARCHITECTURE.md、DATA_MODEL.md、AGENTS.md 或其他仓库事实文档。
- 如果项目记忆与用户明确指定的仓库事实文档冲突，Codex 应提示冲突，不得自行判断哪一方正确。
- MVP 不自动同步项目记忆与仓库文件。
- 用户可以不经过 Codex 直接手动编辑项目记忆。

### 11.12 项目记忆维护对话

- AI 生成项目记忆建议时，用户必须新建一条项目级专用维护对话。
- 普通任务对话不能直接提交项目记忆建议。
- 创建维护对话时必须明确提示项目记忆会影响项目内后续对话。
- 维护对话可以选择零个或多个来源工作项。
- 零个来源工作项适用于初始化项目记忆或纯项目级讨论。
- 选定工作项时，只提供其目标、状态和最新已确认任务记忆。
- 不提供工作项全部原始对话、历史任务记忆、待审核建议或已过期建议。
- 没有已确认任务记忆的工作项可以被选择，但应明确提示只会提供目标和状态。
- 系统同时提供当前最新已确认项目记忆；不存在时使用空白固定分区。
- 用户可以添加本次讨论要求。
- Codex 不在维护对话创建时自动扫描整个项目目录；用户可以在正常权限范围内明确要求检查相关仓库文件。
- 一条维护对话只对应一次项目记忆更新周期。
- 周期内允许讨论、纠正和重新生成当前建议。
- 建议被确认或放弃后，该维护对话不能再次提交项目记忆建议。
- Codex 工作区不可用时，用户仍可手动编辑项目记忆，也可以生成项目级上下文复制到官方 Codex 客户端；外部回复不会自动成为项目记忆建议。

### 11.13 建议生命周期与过期规则

记忆建议具有以下状态：

- 生成中：Codex 正在生成，尚不可审核。
- 待审核：基于当前有效基础版本，可以编辑和确认。
- 已过期：基础版本已被取代，不可直接确认。
- 已确认：已经形成新的正式记忆版本，建议结果不可修改。
- 已放弃：用户明确放弃，保留用于追溯。

生成失败不形成建议，只记录失败结果和可重试信息。

过期规则：

- 每份任务记忆建议记录其基础任务记忆版本；没有版本时记录为空白基础。
- 确认一份任务记忆建议后，其他基于旧任务记忆版本的待审核建议立即过期。
- 每份项目记忆建议记录基础项目记忆版本，以及所选工作项的确切任务记忆版本。
- 当基础项目记忆或本次固定的来源版本发生变化时，维护对话不得悄悄刷新来源；用户应新建维护对话重新生成建议。
- MVP 不自动合并过期建议或解决语义冲突。

### 11.14 差异、编辑与确认

- 任何 AI 生成建议在确认前必须展示相对于基础版本的增加、修改和删除。
- 用户可以在确认前编辑所有记忆分区。
- 用户编辑应持续保留，允许离开页面后继续审核。
- 与工作项目标、状态、当前进度、下一步或阻塞原因相关的字段建议应在同一次审核中单独展示。
- 工作项字段不得因记忆变化而自动修改，必须由用户明确确认。
- 确认真正保存成功前，后续对话继续使用旧的已确认记忆。
- 重试确认不得生成用户不知情的重复版本。
- 已确认版本不可原地编辑；后续修改产生新版本。

### 11.15 手动编辑记忆

- 用户可以从当前已确认版本进入手动编辑。
- 保存前展示差异并要求确认。
- 确认后形成新的不可变版本。
- 来源标记为用户手动编辑，不关联虚构的来源对话。
- 手动编辑项目记忆不要求创建维护对话。
- 手动编辑任务记忆不要求进入普通任务对话。
- 如果编辑期间基础版本发生变化，当前编辑应标记为过期并要求重新核对。
- MVP 不要求用户填写修改理由。

### 11.16 版本级追溯

每个已确认记忆版本至少能够追溯：

- 确认时间
- 前一版本
- 基础版本
- 来源类型：Codex 建议或用户手动编辑
- 来源对话（适用时）
- 项目记忆建议所选的来源工作项和任务记忆版本（适用时）
- AI 原始建议（适用时）
- 用户确认前的编辑结果
- 同时发生的工作项字段变化（适用时）

MVP 不要求记忆中的每句话引用具体原始消息。

### 11.17 归档

- 项目和工作项都可以归档和取消归档。
- 归档不是工作项状态，不改变工作项的原状态。
- 归档对象默认不出现在活动列表，但仍可搜索和查看。
- 归档保留工作项、记忆版本、建议和对话关联。
- 归档项目时，其工作项一起退出活动视图。
- 取消归档项目不得改变各工作项原有状态。

### 11.18 永久删除

- 永久删除只能从已归档对象发起。
- 删除前必须展示影响范围并进行二次确认。
- 删除工作项会删除 AIKanBan 本地保存的工作项数据、记忆、建议和对话关联。
- 删除项目会删除 AIKanBan 本地保存的项目记忆、维护对话关联、所属工作项及其管理数据。
- 永久删除不得删除、移动或修改关联代码目录及其文件。
- 永久删除不得声称删除 Codex 一侧保存的原始对话。
- MVP 不承诺产品内恢复永久删除的数据，确认界面必须明确说明。

## 12. 空状态

### 12.1 无项目

- 解释项目是工作项、目录和记忆的容器。
- 提供创建项目入口。
- 明确创建项目需要项目名称和有效本地目录。

### 12.2 新项目无项目记忆

- 明确显示尚无已确认项目记忆。
- 提供手动创建入口。
- Codex 工作区可用时，提供与 Codex 讨论并创建基础项目记忆的入口。
- Codex 工作区不可用时，提供生成项目级上下文并复制的入口。
- 项目记忆空状态本身不阻止创建工作项；Codex 工作区可用时也不阻止创建普通对话。

### 12.3 项目无工作项

- 提供创建第一个工作项入口。
- 简要说明工作项用于组织目标、状态、多条对话和任务记忆。

### 12.4 工作项无任务记忆

- 明确显示尚无已确认任务记忆。
- 不制造空白已确认版本。
- Codex 工作区可用时，允许创建第一条对话。
- 始终允许手动创建记忆；工作区不可用时允许生成上下文并复制。

### 12.5 工作项无对话

- Codex 工作区可用时，提供创建新对话入口。
- Codex 工作区不可用时，提供“生成上下文并复制”入口。

### 12.6 Codex 工作区不可用

- 显示工作区不可用的具体检查阶段和可理解原因。
- 提供与 CLI、兼容性、握手或认证问题相匹配的修复指引。
- 项目、工作项、记忆、版本和归档入口保持可用。
- 在需要开始外部对话时，提供“生成上下文并复制”入口。
- 不提供解析内部 Codex 数据或导入外部 thread 的绕过操作。

### 12.7 无待审核建议

- 说明只有用户手动触发后才会生成建议。
- 不用自动生成内容填充空状态。

## 13. 错误状态与恢复体验

### 13.1 对话创建失败

- 显示失败阶段和可理解的错误信息。
- 不创建看似成功但无法打开的关联。
- 保留用户尚未发送的提示和上下文补充。
- 用户修复登录、网络、目录或权限问题后可以重试。

### 13.2 Codex 工作区启动失败

- Codex CLI、版本和 schema、App Server 握手或认证检查任一失败时，工作区失败关闭。
- 显示准确的失败类别和修复指引，不把认证上下文不可访问笼统映射为网络错误。
- 如果 Codex CLI 可以启动但当前运行上下文无法访问认证，明确提示用户在 AIKanBan 可访问的 Codex 运行环境中完成或修复登录。
- 不读取、复制或展示 Codex 认证文件、token 或账号敏感信息。
- 项目、工作项和记忆管理保持可用。
- 用户可以生成上下文并复制到官方 Codex 客户端。

### 13.3 对话运行中断

- 区分运行失败、用户停止、浏览器连接中断、后端或 App Server 退出、等待确认和需要重新核对。
- 只有 AIKanBan 所属 App Server 实际发出未解决审批请求时，才能显示等待确认。
- 浏览器连接中断但后端和 App Server 仍存活时，不得立即假定 Codex 运行失败；后端继续维护最近已知状态和已完成事件。
- 浏览器恢复连接后，先恢复 AIKanBan 自有状态缓存，再通过公开 Codex 能力核对实际历史和当前可见状态。
- AIKanBan 后端或 App Server 退出后，不保证活动 turn 继续执行、可读取或可恢复。
- 后端或 App Server 异常退出后，原活动对话显示“需要重新核对”，不伪装为正在运行、已完成、已停止或失败。
- 无法判断其他 Codex 客户端是否正在使用同一 thread；AIKanBan 显示的状态不得宣称为全局状态。
- 用户请求停止后先显示正在停止，收到确认后再显示已停止。

### 13.4 记忆建议生成失败

- 当前已确认记忆保持不变。
- 不产生空白或不完整的待审核建议。
- 保留生成请求所基于的版本和用户补充要求，以便重试。
- 如果 Codex 返回可读内容但无法形成预期分区，允许查看原始回复和重新生成。
- 不得自动把无法解析的原始回复写入正式记忆。
- 重试时如果基础版本已经更新，应基于最新版本重新生成。

### 13.5 审核或保存失败

- 保留用户对建议所作的编辑。
- 明确显示尚未确认成功。
- 保存成功前继续使用旧的已确认记忆。
- 重试必须避免重复版本。

### 13.6 目录不可用

- 显示目录不可用状态和原路径。
- 保留所有管理数据和历史。
- 阻止创建新的普通任务对话。
- 提供重新关联入口。

### 13.7 过期建议

- 明确显示基础版本和当前最新版本。
- 禁止直接确认。
- 允许用户查看、放弃或基于最新版本重新生成。
- 不自动合并差异。

## 14. 用户可见的隐私与本地数据原则

### 14.1 保存在本机的数据

MVP 在本机保存：

- 项目、工作项、状态和目录关联
- 项目记忆和任务记忆的版本历史
- 待审核、已过期和已放弃的记忆建议
- Codex 对话关联和产品正常运行所需的本地缓存
- 用户界面偏好

MVP 不提供 AIKanBan 云账号、云同步、远程备份或默认产品遥测。

AIKanBan 不把 Codex 内部 rollout、状态数据库或认证文件复制为自身的管理数据来源。

### 14.2 可能发送给 Codex 的内容

以下操作可能向 Codex 提供管理上下文：

- 创建新对话
- 向已有对话发送最新上下文
- 生成任务记忆建议
- 生成项目记忆建议

内容可能包括：

- 项目记忆
- 任务记忆
- 工作项目标、状态、进度、下一步和阻塞原因
- 用户为本次对话输入的补充说明
- 用户在对话中主动提供的其他内容

Codex 在开发任务中还可能根据其权限读取代码文件、运行命令并产生工具输出。AIKanBan 不得把此类交互宣传为所有处理均在本机完成。

### 14.3 用户可见承诺

- 产品只监听本机地址，不默认向局域网或公网开放。
- 产品不设置 AIKanBan 自有云服务。
- 产品不在用户不知情时上传整个项目目录。
- 发送长期记忆前提供可见上下文。
- 产品不把检测到的密钥或敏感内容自动加入记忆。
- 日志和错误信息不记录完整敏感输入、凭据或不必要的代码内容。
- AIKanBan 不读取、复制或保存 Codex 的认证文件和 token，只显示完成工作区可用性判断所需的非敏感认证状态。
- “生成上下文并复制”只把用户已预览的内容交给本机剪贴板；内容只有在用户主动粘贴到官方 Codex 客户端后才进入该客户端。
- 永久删除只删除 AIKanBan 本地保存的数据，不声称同步删除 Codex 一侧数据。
- 产品清楚区分本地保存和发送给 Codex 处理。

## 15. 功能验收标准

### 15.1 项目和目录

- 用户不能在未选择有效目录时创建项目。
- 用户不能用与另一个未归档项目相同的规范化目录创建项目。
- 嵌套目录得到明确提示，并可由用户确认继续。
- 项目创建后，其 AIKanBan 管理的 thread 全部使用该项目指定的精确目录。
- 用户不能为单条 thread 选择项目目录下的其他子目录。
- 目录失效后，项目管理数据仍可查看和编辑。
- 目录失效后不能创建新的普通任务对话。
- 重新关联目录不会移动、复制或删除任何代码文件。

### 15.2 工作项

- 用户必须填写标题和目标才能创建工作项。
- 新工作项默认状态为未开始且没有任务记忆版本。
- 已阻塞状态要求阻塞原因。
- 用户可以在五种固定状态之间明确切换。
- AI 建议的状态变化不会未经确认直接生效。

### 15.3 新建普通对话

- Codex 工作区可用时，用户能在工作项中创建新的、由 AIKanBan 管理的 Codex 对话。
- 发送前能看到最新项目记忆、工作项信息、最新任务记忆和一次性说明。
- 无项目记忆或任务记忆时显示明确空状态，但仍可创建对话。
- 待审核和已过期建议不会被当作正式上下文发送。
- Codex 工作区不可用时，用户能生成相同上下文预览并复制，但不会创建或关联 thread。

### 15.4 浏览器对话工作区

- 工作区只有在 CLI、版本和 schema、握手及认证检查全部通过后才可用。
- 用户能查看 AIKanBan 管理的对话历史、发送提示并看到当前 App Server 能够确认的运行状态。
- 用户能停止当前运行并看到停止过程的真实状态。
- AIKanBan 所属 App Server 实际发出的审批请求能够在浏览器中处理，并绑定准确请求。
- 产品不声称能够检测其他 Codex 客户端是否正在运行同一 thread。
- 浏览器断线但后端仍存活时，重连后能恢复最近已知状态并核对。
- 后端或 App Server 退出后，原活动对话显示“需要重新核对”，且不承诺活动 turn 延续。

### 15.5 对话关联、重新关联和复制降级

- 一条由 AIKanBan 创建的普通对话不能同时关联两个工作项。
- 重新关联不会转移记忆或删除原始对话。
- 历史版本仍能显示该对话原先作为来源的关系。
- 产品不提供既有或外部 Codex thread 的发现、导入或接管入口。
- 工作区不可用时，用户能复制已预览上下文到官方 Codex 客户端。
- 复制流程不创建本地对话关联、不跟踪外部状态，也不自动获取外部回复。

### 15.6 任务记忆

- 用户能从普通任务对话手动生成建议。
- 建议使用六个固定分区。
- 用户能查看相对于基础版本的增加、修改和删除。
- 用户能编辑建议并明确确认或放弃。
- 确认后形成不可变新版本。
- 未确认建议不会成为后续对话的正式上下文。
- 用户能不经过 Codex 直接编辑并版本化任务记忆。

### 15.7 项目记忆

- 用户能手动创建和编辑项目记忆。
- Codex 工作区可用时，用户能创建不选择工作项的维护对话，用于生成基础项目记忆。
- Codex 工作区可用时，用户能选择多个工作项创建维护对话。
- 系统只提供所选工作项的目标、状态和最新已确认任务记忆。
- 项目记忆建议使用五个固定分区。
- 一条维护对话在确认或放弃后不能开始第二个更新周期。
- 未确认项目记忆建议不会影响后续普通对话。

### 15.8 并发和过期建议

- 多条普通对话可以生成多份待审核任务记忆建议。
- 确认其中一份后，其他旧基础建议立即变为已过期。
- 已过期建议不能直接确认。
- 用户可以查看、放弃或重新生成已过期建议。
- 系统不自动合并内容。

### 15.9 上下文刷新

- 对话使用的记忆落后时显示上下文已过期。
- 用户可以预览并手动发送最新上下文。
- 记忆更新不会自动推送到已有对话。
- 上下文版本未知与运行状态“需要重新核对”能够被清楚区分。

### 15.10 版本追溯

- 每个确认版本能够查看前一版本、基础版本、来源类型和确认结果。
- Codex 生成的版本能够关联来源对话和 AI 原始建议。
- 项目记忆版本能够显示所选来源工作项及其任务记忆版本。
- 手动编辑版本清楚标记为用户手动编辑。

### 15.11 错误恢复

- CLI、版本或 schema、握手和认证失败会关闭 Codex 工作区，并显示对应修复指引。
- 工作区关闭时，项目、工作项和记忆管理仍然可用。
- 工作区关闭时，用户仍能生成上下文并复制。
- 浏览器断线和后端或 App Server 退出显示不同的恢复路径。
- 无法核对活动对话时显示“需要重新核对”，不映射为已完成。
- 生成失败不会改变当前已确认记忆。
- 保存失败会保留用户编辑并清楚显示尚未确认。
- 重试不会产生重复版本。

### 15.12 归档和删除

- 用户能归档和恢复项目与工作项。
- 归档不改变工作项状态或删除历史。
- 永久删除只能从已归档对象发起。
- 删除前显示影响范围和不可恢复说明。
- 永久删除不影响代码目录和 Codex 原始对话。

### 15.13 隐私护栏

- 产品默认只通过 localhost 提供界面。
- 用户能够区分本机保存数据和发送给 Codex 的内容。
- 长期记忆在发送前可见。
- 复制到剪贴板的上下文在用户主动粘贴前不会自动发送给 Codex。
- 产品不设置 AIKanBan 云同步或默认遥测。

## 16. 风险、假设与待决问题

### 16.1 产品风险

#### 审核负担过高

用户可能因为频繁查看差异而放弃更新记忆。MVP 应保持固定分区简洁、差异清晰，并坚持手动触发，避免制造无意义建议。

#### 记忆逐渐膨胀

如果每次更新只增加内容，后续上下文会变得冗长。生成规则必须允许删除失效内容，并强调记忆是交接上下文而不是完整日志。

#### 项目记忆污染

局部任务结论可能被错误提升到项目层。MVP 通过专用维护对话、明确来源工作项、只使用已确认任务记忆和再次人工确认降低风险。

#### 多对话冲突

并行对话可能产生相互冲突的建议。MVP 只进行版本过期检测，不承诺自动语义合并。

#### 工作项字段与任务记忆不一致

目标、进展和下一步可能同时出现在工作项摘要与任务记忆中。MVP 在同一次审核中展示关联字段建议，但不得静默同步。

#### 用户误解本机产品为完全离线

产品必须持续说明 AIKanBan 管理数据在本机保存，但 Codex 交互可能将内容发送到外部服务。

### 16.2 集成风险

- Codex App Server 已经能够支撑 AIKanBan 自建 thread 的最小闭环，但当前仍是受版本约束的实验性集成面。
- Codex 版本和 schema 可能变化；未通过兼容性检查时必须关闭工作区，而不是尝试兼容未知协议。
- 相同 Codex CLI 在不同运行上下文中可能获得不同认证状态，部署方式不正确会导致工作区不可用。
- 浏览器断线可以由仍存活的后端缓存并核对；后端或 App Server 退出则不保证活动 turn 延续。
- AIKanBan 无法可靠检测其他 Codex 客户端或 App Server 是否正在运行同一 thread。
- 历史发现范围、cwd 过滤和任意子目录归属尚未可靠验证，因此不属于首版能力。
- 审批 UI 只能响应当前 AIKanBan 所属 App Server 实际发出的请求，不能主动保证所有审批类型都会出现。

### 16.3 数据与恢复风险

- MVP 没有云备份，用户机器故障可能导致本地管理数据丢失。
- 永久删除在产品内不可恢复。
- 应用升级必须保护已有记忆和关联数据；具体迁移策略由数据模型和架构设计确定。
- 后端或 App Server 异常退出时，活动 turn 可能没有可恢复的持久化结果；AIKanBan 必须保留自己的管理数据并清楚标记需要重新核对。

### 16.4 暂定假设

- 在受支持版本和正确用户认证上下文中，AIKanBan 后端能够启动并维持其所属 Codex App Server。
- 对 AIKanBan 自己创建并管理的已持久化 thread，公开能力足以创建、读取已完成历史、继续和停止。
- 浏览器能够呈现当前 AIKanBan 所属 App Server 实际发出的审批请求。
- 应用能够在重启后恢复本地管理数据、版本历史及 thread 关联，但不假设异常退出时的活动 turn 能继续。
- MVP 不需要产品遥测即可通过自用验收判断核心闭环是否成立。
- 页面布局、视觉样式、默认排序和具体导航不影响当前产品需求判断。

### 16.5 已确认的架构输入

- AIKanBan 后端持有并管理自己的长期 App Server 进程，浏览器不直接把 App Server 当作权威状态源。
- 启用 Codex 工作区前必须完成 CLI、版本和 schema、握手及非敏感认证状态检查。
- App Server 响应和事件必须在系统边界进行运行时校验，生成 schema 不能被视为跨版本永久契约。
- 只有本 App Server 管理的活动 thread 可以显示精确实时状态；不得从 notLoaded 推断已完成。
- 浏览器断线恢复依赖 AIKanBan 自有的最近状态和完成事件缓存，并通过公开 thread 读取能力核对。
- 后端或 App Server 退出后不保证活动 turn 延续，重启后原活动对话进入“需要重新核对”。
- 审批只处理当前 App Server 实际发出的准确请求。
- 不读取或写入 Codex rollout、状态数据库、认证缓存或其他未公开内部接口。
- 工作区失败关闭时，本地管理功能和“生成上下文并复制”流程保持可用。

### 16.6 架构阶段仍待决问题

- Codex 支持版本范围、schema 生成或匹配方式和升级流程
- 独立 Codex CLI 的定位、启动和用户可理解的安装修复流程
- Codex 登录状态不可访问时的具体修复引导
- 浏览器与后端之间的状态缓存、订阅和重连协议
- 本地数据存储、备份、升级和恢复策略
- 凭据与敏感日志的具体保护方式
- 路径规范化和目录权限校验规则
- “需要重新核对”的具体核对动作、失败重试和最终状态呈现

## 17. MVP 后可能方向

以下方向仅供未来评估，不属于当前范围或交付承诺：

- 将 AIKanBan 做成官方 Codex 插件，通过本机 MCP 服务和可选内嵌 UI 提供工作项与记忆操作。
- 在完成数据影响和并发状态验证后，重新评估既有或外部 Codex thread 的受控导入。
- 在完成 cwd 返回和 Windows 路径规范化验证后，评估单条 thread 使用项目任意子目录。
- 如果未来公开能力支持，再评估跨 App Server 或跨客户端全局运行状态检测。
- 如果未来公开能力提供可靠保证，再评估后端退出后活动 turn 的延续和恢复。
- 从任务记忆中辅助提出“提升为项目记忆”的候选内容。
- 为过期建议提供辅助对比和人工合并界面。
- 在不削弱用户确认原则的前提下，提供可配置的记忆更新提醒。
- 提供可选的本地备份、导出和恢复能力。
- 在真实单用户闭环验证后，再评估团队协作、远程访问或其他 AI 提供方。

任何后续方向在进入范围前，都需要单独验证问题、价值、隐私影响和复杂度，并更新本文档或创建相应独立需求文档。
