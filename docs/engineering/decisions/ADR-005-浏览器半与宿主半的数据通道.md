# ADR-005：浏览器半与宿主半的数据通道

| 信息 | 内容 |
| --- | --- |
| 日期 | 2026-10-14 |
| 状态 | 提议 |
| 影响功能 | F01、F02、F03、F04、F11、F15、F16、F17、F19、F20（所有需要在看板界面里读写正式数据的入口） |
| 被替代关系 | 无 |

## 要解决的问题

看板的全部可见内容（任务、状态、概况、总览、待确认）都由 host 半持有并持久化，而界面在浏览器半。需要确定浏览器半用什么通道读取与写入 host 半的数据。

这不是实现细节：它决定权限边界（数据是否暴露给本机其他进程）、决定 `packages/core` 能否被两端共用、也决定后续 F04/F06/F11 等要在 host 半发起真实会话动作时，界面如何获知结果。ADR-004 只定了界面挂在哪些座位，没有覆盖数据从哪来。

## 可核对的宿主事实

以下三条来自本机已安装包与活动宿主的只读检查：

1. **浏览器半拿不到网络能力。** `@deepseek-ai/dsh-cordis-client-runner` 的 README 明确写道：浏览器半以纯 JavaScript 编写、无模块导入，运行时「receives a fixed set of names — `React`, `console`, `styles`, and `host` — while browser globals like `fetch` and `setTimeout` are unavailable」。
2. **`host.call` 是设计给这条路的。** 同一份 README：「Calling `host.call(method, args)` from the loaded half reaches its own host half」，并且「`host.call` routes through the Remote namespace; an omitted argument travels as `null`, and a payload the generated codec refuses becomes a teaching error naming the call and the contract」。
3. **活动宿主把它描述为包内私有。** `cordis_inspect_query`（platform `client`, provider `Builtin`）返回：`host` — *"Package-private JSON RPC from Client to this Package's Host half"*，签名 `host.call(method: string, args?: JsonValue): Promise<JsonValue>`。

补充事实（用于排除其他方案）：已安装的第三方插件 `@omdsh-dev/dsh-genui` 的 host 半通过 `ctx.webServer.register` 注册路由，但那**只用于服务它自己的静态资源**；它的 client 半 `inject: []`，不向 host 半取任何数据。它证明 host 半可以用 webserver，**不**证明那是客户端取数的通道。`dsh-host-webserver` 的 README 说明该服务「no TLS, authentication, or origin policy of its own」，默认绑定 `127.0.0.1`，由路由所有者自行实施请求策略。

## 可选方案

| 方案 | 说明 | 结论 |
| --- | --- | --- |
| A. host 半注册本机 HTTP 路由，client 半请求 | 用 `ctx.webServer.register` 暴露数据接口 | **拒绝**：该服务无 TLS/认证/同源策略，等于把看板数据开放给本机任意进程，需要自造令牌与防护 |
| B. `host.call(method, args)` | 动态 Cordis 包的沙箱内私有 JSON-RPC | **拒绝**：只存在于动态包沙箱，普通 Loader 插件无法注册（见下） |
| C. client 半自持数据 | 界面只用自己的内存/浏览器存储 | **拒绝**：违反 OBJ-01 的项目隔离与 REC-01 的持久化合同，也会与 host 半形成两份事实源 |
| D. 把数据塞进槽位或共享服务传递 | 借 `slots`/共享 client 服务中转 | **拒绝**：把数据通道与呈现机制耦合，且 client 服务目录里没有合适的中立座位 |
| E. 不做通道，S1 只交付未接线的 UI | 界面留占位状态 | **拒绝**：S1 的验收要求真实可用的看板；用假界面冒充阶段闭环违背「只出现空壳不能写为完成」 |
| F. `ctx.connection.rpc` 已鉴权通道 | host 半注册通道前缀，client 半按端点调用 | **采用** |

## 采用方案

**方案 F：`ctx.connection.rpc`。** 宿主半用 `ctx.connection.rpc.handle(channel, handler)` 注册一个**已鉴权的**通道前缀，浏览器半用 `ctx.connection.rpc.call(channel, endpoint, payload, signal)` 调用。

### 被否决方案 B 的依据（保留以便追溯）

`host.call` 曾在本 ADR 第一版被采纳，复核后被否决：

- `host.call` 与宿主侧的 `harness.handle` 成对存在，而 `harness` 只存在于**动态 Cordis 包**的沙箱符号表里（`dsh-cordis-host-runner/lib/index.js` 的沙箱符号目录列出 `name: "harness"`；其 README 说明动态包的 host 半运行在 `node:vm` 沙箱中）。本插件是 `cordis.patch.yml` 加载的**普通 Loader 插件**，host 半永远拿不到 `harness`，因此**没有注册 `host.call` 方法的途径**。
- 动态包的浏览器半由 `dsh-cordis-client-runner/lib/client.js` 以 `["React", …, "styles", "host"]` 作为闭包参数求值；其失败文案也点名 `harness.handle`。我们的 bundle 半只拿到一个 `require` 参数（`dsh-client-modules/lib/client.js` 的 `factory: (require) => …`），`host` 既不是模块也不是种子词，**调用它会抛 `ReferenceError`**。
- 本会话早先引用的 `Builtin` 目录里那条 "available to a dynamic Client half" 描述，只适用于动态包，不适用本插件形态。
- 同时更正第一版的一处错误推论：**bundle 半是注入 `<head>` 的普通脚本，拥有真实浏览器全局**（`fetch`、`setTimeout`、`document` 均可用）。第一版写「浏览器半没有 `fetch`/`setTimeout`」是把动态包求值器的文档误用到了 bundle 形态上，该限制不成立。

### 通道结构

```
packages/core           纯逻辑：模型、版本链、成对确认、校验器
      ↑ 仅 host 半 import
packages/plugin         host 半：打开 domain、注册 /aikanban 通道、注册 AI 工具
      ↕ ctx.connection.rpc —— 已鉴权、同源、由宿主既有传输承载；无自建路由、无自造令牌
packages/plugin-client  浏览器半：BoardSource 端口 → rpc 适配器 → 看板 UI
```

采用理由（每条都有源码依据）：

1. **鉴权由宿主已有机制承担**：注册的通道在进入我们的 handler **之前**先跑 `requestRejection`（Host/Origin 检查与浏览器令牌），未通过直接 401/403。这正面回答了本机进程暴露问题，因此不需要自造令牌。
2. **生命周期正确**：注册挂在 `owner.effect(...)` 上，随插件 fiber 卸载而注销，不留悬挂路由。
3. **通道名受约束、不会误注册**：通道名须匹配 `^/[A-Za-z0-9._~-]+$`，且保留前缀 `/api` 被拒绝；重复注册会抛错，因此命名冲突是显式失败而非静默覆盖。
4. **不需要改 DSH 源码、不需要官方装配**：这是普通 Loader 插件就能用的通道，与本插件的 bundle 形态相符。

通道与端点约定：

- 通道名：**`/aikanban`**（与包名 `@aikanban/dsh-aikanban` 对齐；端点用段安全命名，如 `board/read`、`task/status.set`、`task/reorder`、`task/status.undo`）。
- 端点名必须等于请求 URL 的末段（宿主侧校验 `message.method === endpoint`）。
- 请求必须是 `POST` + `content-type: application/json`，否则 415。
- **handler 绝不允许抛异常**：抛出的错误会变成 HTTP 500，调用方拿不到结构化失败。所有失败必须以 `{ok:false, error:{code, message, details}}` **返回**。
- 浏览器半采用**容错探测**而不是硬依赖：`inject` 保持最小（`slots`），运行时探测 `ctx.connection`；缺失时按 REC-05 呈现**可见读取失败 + 重试**，而不是把 fiber 卡死在一个没有该服务的组合里。
- 取消：`call` 接受 `signal`，故读取可取消。

## 影响与代价

- 正面：不新增监听端口，不需要自造鉴权；`packages/core` 保持纯逻辑可单测；host 半的导入图仍可保持零 bare specifier（core 由打包器内联），`tools/verify-host-import.mjs` 继续有效；通道随插件 fiber 卸载。
- 代价与限制：
  1. 物理跳转由宿主既有传输承载，**本会话无法做真实网络往返**（那需要写 profile 并重启进程）。因此证据是**协议级往返**（真实构建产物 + 契约一致的信封），不是网络跳转——必须在证据里如实分级，不得写成「端到端已验证」。
  2. 所有 UI 侧数据访问都要经过 `BoardSource` 端口，端口会随功能增长；需在端口分组上保持克制，避免变成万能表。
  3. 每个端点都要自己定义错误码并**返回**失败，异常会被吞成 500。
  4. 浏览器半虽拥有真实浏览器全局（`setTimeout` 可用），但按 REC-01 重试由用户发起，S1 读取默认用户触发而非轮询。
  5. 读取失败必须显式呈现失败与重试，**不得**显示空看板（REC-05），也不得把未接通当作正常空状态。

## 验证证据

- 已有（否决性证据）：`host.call` 不可用。依据是沙箱符号表与 bundle 工厂签名两处源码，加上两份包的 README 说明；见「被否决方案 B 的依据」。
- 已有（接口依据）：`connection` 通道的注册与调用面。宿主侧 `rpc.handle(channel, handler)` 校验通道名、拒绝保留前缀 `/api`、注册为前缀路由、**先跑 `requestRejection` 再进入 handler**，并挂 `owner.effect` 随插件卸载；客户端 `rpc.call(channel, endpoint, payload, signal)` 以 `{type:'client-request', rpcId, method, payload}` POST 并校验回显 `rpcId`；信封契约要求 POST + JSON（否则 415）、`method` 必须等于 URL 末段、handler 抛异常会变成 500。依据均在 `@deepseek-ai/dsh-client-connection`。
- 待补：**协议级往返**——构建产物级的真实往返：宿主半对假 `connection.rpc.handle` 注册 `/aikanban`；浏览器半经假 `window.__ModuleLoader__` 加载构建产物并把真实适配器打进真实 handler；断言端点名、负载、成功信封与失败映射（含 handler 返回 `ok:false` 而非抛出）。隔离宿主探针另断言宿主半确实注册了 `/aikanban`。
- **证据分级（必须如实标注）**：以上是**协议级**往返，不是网络跳转。真实页面 ↔ 宿主进程的网络往返需要写 profile 并重启进程，本阶段不做。因此本 ADR 保持 `提议`；只有在真实 profile 中观察到一次成功调用后，才可改为 `采用`。
- 证据写入 `docs/prd/features/F02-task-status-and-cards/implementation.md`（由 `board` 在 S1 内完成）。

## 尚未验证

以下四项是 **2026-10-22 真实 HTTP 往返取证之后**仍未取得证据的部分。已取证的部分已从本节移出，见本页[「证据（2026-10-22）」](#证据2026-10-22)：隔离宿主上 `POST /aikanban/project/list`、`/aikanban/board/read` 的真实 carrier 往返（HTTP 200 + 合法 `{type:'server-response', rpcId, result}` 信封 + `result.ok=true` 与快照）、围栏 401/403/415/404、以及契约失败以 `ok:false` 返回而非抛成 500——这些**不再**属于「尚未验证」。

- **页面内（真实浏览器）的 `rpc.call` 未观察**：现有证据是进程内契约测试 + 外部脚本构造的 HTTP；没有一次由真实页面在 `window.__DSH_BOOT__` 装配后经 `ctx.connection.rpc.call` 发出的请求。页面侧凭据（`requestRejection` 实际使用的 `dsh-auth-*` 签名 cookie）是否随页面请求自动送出、失败 `details` 的跨通道形状、`signal` 取消语义也都还没有页面内证据，将随这一次页面内观察一并确认。
- **真实 profile 装载未做**：没有把插件装进 `~/.dsh/profiles/desktop`、没有重启 GUI，因此真实 profile 的加载链（bundle 层解析、`dsh.client` 装配、面板渲染）未验证。
- **写端点经真实 HTTP 未取证**：`task/status.set`、`task/reorder`、`task/status.undo` 三个写端点仍只有进程内证据；真实 carrier 上只验证了 `project/list` 与 `board/read` 两个读端点。
- **`tasks` 非空时的看板内容未观察**：隔离宿主里的 core 是全新数据层，`board/read` 返回 `tasks:[]`；非空任务、列内排序、卡片字段在真实快照中的形状未验证。

**转「采用」的条件**：页面内 `rpc.call` 取得 HTTP 200 + 合法 RPC 信封的证据（一次即可；随后更新本节与头部状态行）。

## 宿主缺陷与兼容层（2026-10-21）

**背景（实施期实测，宿主版本 DSH 44.7.0）：公开的 `ctx.connection.rpc.handle` 对本插件不可用。**

安装包证据（`@deepseek-ai/dsh-client-connection`，本机已安装的 44.7.0）：

- `lib/index.js:540-545` —— `get rpc()` 的闭包把 `owner` 固定为服务对象自己的 `this.ctx`：
  ```js
  get rpc() { const owner = this.ctx; return { handle: (c, h) => this.register(owner, c, h) } }
  ```
- 同文件 `:618` —— `register(owner, …)` 内部执行 `owner.effect(() => owner.webServer.register(route), …)`；这是实际抛栈发生的那一行（`owner` 被固定成 provider 的上下文，解析不到 `webServer`）。
- 同包 `lib/types/rpc-host.d.ts` 对 `HostConnectionService` 的声明原文写着 channel registrations **belong to the caller fiber**——即「通道注册归属调用方 fiber」是该服务自己的设计意图；实现（把 `owner` 固定成 provider 的 `this.ctx`）与该意图不符。

实测（isolated probe：从一个**同时注入** `connection` 与 `webServer` 的子 fiber 调用）：

| 调用方式 | 结果 |
| --- | --- |
| `rpc.handle(channel, handler)`（文档路径） | 抛 `cannot get property "webServer" without inject` |
| 宿主内部 `register(owner = 该子 fiber, channel, handler)` | **成功**（route 注册到子 fiber 的 `webServer`） |

结论：失败原因是 `owner` 归属被服务内部改写，不是「调用方漏注入 `webServer`」；公开入口在 44.7.0 上对该形态的插件不可用。

### 兼容层

`packages/plugin/src/scoped-channel-registration.ts` 把差异收在一处：

1. **先走公开路径** `connection.rpc.handle(channel, handler)`——公开入口可用的宿主照常走它，没有版本判断、没有行为分叉；
2. **仅当公开路径抛错**时，回退到宿主自己的 `register(owner = 注入子上下文, channel, handler)`（公开 getter 本应做的同一调用）；
3. 找不到该方法或回退也抛错 → `register-failed`（**绝不静默成功**）。`register-failed` 只存在于 `aikanban:board-channel` 诊断事件与 `BoardChannelRegistration` 的 reason 联合里，**不是浏览器失败码**（8 码不变）：通道未注册时 handler 根本不会被调用，浏览器实际表现为读 `read-failed`、写 `unknown-result`。

### 可删除条件（本层是宿主缺陷的临时工，不是我们的设计）

- 公开路径修好后，兼容分支**自动不再被走到**——没有版本探测需要删，行为自然回到 `public`。
- 观测方式：`aikanban:board-channel` 事件的 payload 自本提交起带 `path`（`public`/`compat`/`failed`/`null`），`tools/probe-host.mjs` 第 5 项同时打印 `path=…`。宿主升级后看到 `path=public` 即可删除兼容分支（乃至整个回退代码）；若兼容分支失效，会以 `path=failed` + 探针第 5 项 FAIL 显式暴露，不会静默退化。
- 删除动作本身不改变本 ADR 的契约结论，因此不需要另开 ADR；本页记录足以追溯。

### 状态

**本 ADR 状态仍为「提议」**，本节不改变它：以上只证明「宿主进程内注册发生 / 路径可行」，真实 `rpc.call` 网络往返仍未验证（见「尚未验证」）。


环境：DSH 44.7.0；隔离 `DSH_HOME`；`--port 0`（端口由系统分配，不写死）；`--no-open`；不写用户 `~/.dsh` 的 profile、不重启 GUI。完整原始输出（含六项门禁）见[实施记录 §14](../s1-wiring-implementation.md)。

**观察到的原始事实**（一次真实运行的摘要；token/cookie 值已脱敏）：

- 宿主 URL（端口由系统分配，非写死）：`dsh web: http://127.0.0.1:10306/?token=<redacted>`。
- 鉴权交换：`GET /?token=…`（`redirect:'manual'`）→ **303** + `set-cookie: dsh-auth-…`；带该 cookie `GET /` → **200**（27899B，含 `__DSH_BOOT__`）。
- `POST /aikanban/project/list`，请求头 `Host: 127.0.0.1:10306`、同源 `Origin`、cookie、`content-type: application/json`，请求体 `{"type":"client-request","rpcId":"…","method":"project/list","payload":{}}` → **200**，响应体 `{"type":"server-response","rpcId":"…","result":{"ok":true,"value":{"projects":[{"projectId":"03696d17-…","title":"AIKanBan",…},{"projectId":"455306c1-…","title":"dsh-plugin（旧）",…}]}}}`；`rpcId` 回显。
- `POST /aikanban/board/read`，payload `{"projectId":"03696d17-…"}` → **200**，`result.ok=true`；value 含 `project:{projectId,title,path,workScopeAvailability:"ok",workScopeAllowed:true}`、`tasks:[]`、`columns:[todo,doing,blocked,done,cancelled]`（各含 `label`/`collapsedByDefault`）、`boardToken:"…"`、`capabilities:{statusChange:true,reorder:true,undo:true}`。
- 围栏负向（同一 cookie；每次只改一个请求属性）：无 cookie → **401**；`Origin: https://evil.example` → **403**；`content-type: text/plain` → **415**；`GET` → **404**；路径 `/aikanban`（无 endpoint 段）→ **404**；补充 `Host: evil.example:1234` → **403**；随后同 cookie 对照请求 → **200 + `result.ok=true`**。
- 契约失败在 HTTP 上的形状：`/aikanban/does-not-exist` → **200** + `result.ok=false, error.code="unknown-endpoint"`；`board/read` 携带未登记 `projectId` → **200** + `error.code="unknown-project"`。
- 进程内注册（diagnostics `aikanban:board-channel`）：`channel="/aikanban", registered=true, path="compat"`；同次运行最后一个 `aikanban:activation` 显示 `dataLayerReady=true`。
- 同次运行六项既有门禁：typecheck / build / 用例 252 / verify 11-11 / probe 5-5 / check_docs（59 md）均通过；原始输出见实施记录 §14.5。

**这些事实的边界**：

- 属于 **carrier 层**的事实：在隔离宿主真实监听的端口上，`/aikanban/<endpoint>` 按宿主实现完成 Host/Origin/cookie/content-type/method 检查后返回了合法的 RPC 信封与看板快照；handler 的失败以信封返回（HTTP 200 + `ok:false`），未抛成 500。
- **不属于**本节的结论：页面内 `ctx.connection.rpc.call` 的真实往返（浏览器半未参与）、真实 profile/GUI 的往返、`ctx.connection.rpc.handle` 公开入口可用。注册路径仍是 `path=compat`（见「宿主缺陷与兼容层」）；「通道上的真实请求确实通」与「注册走兼容路径」是两条独立事实，本节不把它们合并。
- 本节的 workspace 来自探针设施写入隔离 home 的 durable workspace 记录；`board/read` 的 `project` 登记由适配层在同一请求内触发。产品的 workspace 创建入口（GUI/宿主 API）未在本节经过。

**仍未观察**（沿用「尚未验证」一节，且不因本节改变）：真实 profile/GUI 的页面 ↔ 宿主往返；页面侧浏览器令牌的取得；`details` 跨通道的稳健性；取消语义（`signal` 的实际生效点）。本 ADR 状态不变。
