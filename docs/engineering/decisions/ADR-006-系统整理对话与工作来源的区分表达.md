## 1. 要解决的问题

HOST-07 要求「系统创建整理对话、保留本次过程、草稿与结果核对，**区别工作来源和生成过程**」（[宿主能力合同](../host-capabilities.md)）。当前 `sessionController.create({workspaceId})` 建独立会话已验证，但**「保留本次过程」的读取路径**与**「工作来源 vs 生成过程」的区分表达尚未设计**（[架构准备](../architecture.md)「尚未决定的工程项」第 3 条）。

不解决会同时违反三条已确定的产品规则：

- OBJ-04 要求整理对话「不计入任务工作对话、工作数量或未形成记录提示，不允许绑定为工作对话」，并明确「工作成果来源与整理过程来源分别标记」（[对象与状态](../../prd/common/objects-and-states.md)）。
- F13-R03 要求「本次整理对话归当前项目并标明成果来源任务，独立于工作对话……不允许改成其他任务工作对话」（[F13](../../prd/features/F13-project-record-workflow/prd.md)）。
- F13-R04 要求「记录来源为实际工作对话的正式任务记录及其版本，系统整理对话另标生成过程来源」。

因此需要回答四层：**数据层**怎么标记、**读取层**怎么看本次过程、**展示层**怎么分列来源与生成过程、**与 F06 的差别**在哪里。

## 2. 可核对的事实与不可改的产品约束

**宿主侧事实（沿用既有记录，不新增强断言）**

- `create({workspaceId})` 可创建独立会话并挂载项目：已在隔离宿主验证（HOST-02/HOST-07「部分接入」）。
- 会话读取有三条可用通道（`inspect` / `follow` / `page`），S0 已证明对同一份日志一致；但**尚未在「系统整理对话」这一具体场景验证**（HOST-07「保留本次过程」仍标未验证）。
- `workspace.sessionIds` 是**按规范化 `cwd` 过滤的派生视图，不是历史**，不能承担「这条会话是整理对话」的语义（HOST-06、ADR-003）。
- 派发到会话的整理要求落库为 `source.kind='user'`（ADR-001 第 6 节），所以**消息级来源字段无法用来区分会话身份**；区分必须落在会话级。

**不可改的产品约束（本 ADR 不重新定义）**

- F06/F07 的任务记录整理**在原工作对话内**发生，不新建对话；F13 的项目记录整理才**系统新建**整理对话（OBJ-04、F13-R03）。
- 同次失败重试、已有草稿打开、审核更新建议**沿用同一执行载体**；每次新整理使用新对话（OBJ-04、F13-R03）。
- 固定归属、成对保存、历史隔离、人工修正的产品语义不变（[技术决策](README.md)边界）。

## 3. 数据层：系统整理对话如何被标记

**推荐标记方式**：由本插件在自己的归属数据里登记一条显式的「整理会话」记录，不依赖宿主会话标题、不依赖消息来源字段。

- 归属键：`consolidation/{sessionId}`，放**独立 `consolidation` 域**（2026-10-20 用户确认 B1；不是项目 unit 内的子键），与 ADR-002 的 `storageDomain` 布局规则一致，随项目数据一起持久化。
- 字段（建议，命名可在实现时微调，语义不得变）：
  - `workspaceId`：归属项目，对应 OBJ-01 的项目边界；
  - `sourceTaskId`：本次整理针对的**来源任务**，对应 F13-R03「标明成果来源任务」；
  - `runId`：本次整理的稳定标识，供 REC-03「结果未知先核对」与 ADR-001 的幂等 id 对齐；
  - `purpose`：`project-record`（项目记录生成/更新）或 `overview-refresh`（独立手动总览的 AI 核对，CTX-09 允许系统新建整理对话）；
  - `state`：`active`（进行中）/ `confirmed`（已确认）/ `abandoned`（取消或放弃）/ `failed`（整理失败）；
  - `createdAt`、`updatedAt`。
- **结果侧反向指针**（与上面的会话标记双向可核对）：F13 的项目记录草稿与正式版本上记录 `provenance = { kind: 'system-consolidation', sessionId, runId, sourceTaskId, sourceRecordRefs[], cutoff }`，其中 `sourceRecordRefs` 逐条指向实际工作对话的正式任务记录**及其版本**（F13-R04），`cutoff` 是成果截止。
- **工作对话集合的计算**：`工作对话 = workspace.sessionIds − { consolidation/* 的 sessionId }`。这是 OBJ-04「不计工作对话列表/数量、不产生未形成记录提示」与 F13-R03 的实现点。
- **绑定拒绝**：F05/OBJ-03 的绑定路径写入前先查 `consolidation/{sessionId}`，命中即拒绝并说明「系统整理对话不能作为任务工作对话」（OBJ-04、F13-R03）。
- **重启与损坏**：归属记录按 REC-03/REC-05 处理——重启后标记与草稿一起恢复；归属数据不可读时**不得默认把未知会话当成工作对话**，显示需核对而不是静默计入。

**与现有字段的关系**：`source.kind='plugin'` 是**消息级**背景注入标记（ADR-003），不用于会话身份；`session/title` 由用户与模型都可能改写（HOST-02 标题写入本身未验证），因此**不能**作为区分依据。

## 4. 读取层：用户如何查看「本次整理过程」

- **入口**：F13 §3 第 5 步「查看整理对话」按钮，位于任务详情的生成进度面板内，不新增导航层级。
- **形态**：同一面板内的**只读回放**——不提供输入框，不允许继续发送，不提供「从这里继续工作」（避免把过程当工作对话）。
- **范围（2026-10-20 用户确认 B3）**：**摘要优先**——默认展示「整理要求 + 结果 + 状态」；读取失败时降级为**仅状态**并明确标注「过程内容不可读」，不冒充完整过程，也不静默留空。
- **不可复制（B4）**：过程内容不提供复制入口与复制动作；CTX-10 的复制规则只针对当前背景，不适用于过程材料。
- **不授权历史、不进默认背景**：查看过程**不登记 CTX-05 的「实际使用」**，不进入 CTX-01/CTX-02 的默认材料，不推进 OBJ-08 的新内容提醒处理位置，不改变任何正式内容；「查看过程不执行工作」（OBJ-04）。
- **失败与结果未知**：显示需核对对象，沿用 ADR-001「幂等 id + 独立送达确认」，不自动重发（REC-03）。
- **与 F12 的边界**：过程内容**不是**正式材料；F12 检索与复制的对象仍是四类正式内容（OBJ-05），过程对话不进入检索结果（F12-R03/F12-R05）。

## 5. 展示层：「来源」与「生成过程」分列

| 位置 | 「来源」表达 | 「生成过程」表达 |
| --- | --- | --- |
| 项目成果详情 | 分区「来源」：来源任务、实际工作对话、所采用的正式任务记录及其版本、截止 | 分区「生成过程」：整理会话、`runId`、时间、状态、只读查看入口 |
| 集中待确认列表（F15 §3 第 3 步） | 每项显示「来源对话 / 成果任务」 | 同一项并列显示「生成过程（系统整理）」，可展开但默认收起 |
| 任务详情生成进度 | 列出缺失来源与本次采用的来源范围（F13-R02） | 进度、取消/重试、查看过程（F13 §3 第 5 步） |
| 项目对话列表 | 只列工作对话（按第 3 节扣除后的集合） | 整理对话**归入「整理过程」分组可见**（2026-10-20 用户确认 B2），并带用户可见标签**「系统整理」**（B5）；不计入工作数量与「未形成记录」提示 |

硬约束：项目记录正文**不得**引用整理对话内容作为成果来源，来源只能是正式任务记录、用户补充或已确认修正（F13-R04、F13 §7）；成果、总览与工作记录分别存在，不能合并成一份改名后的材料（F13 §7）。F15-R01 的「一组记录与总览候选只计一项」不受本设计影响：过程对话不产生额外确认项。

## 6. 与 F06 的区别：为什么任务记录整理不需要这一层

| 维度 | F06/F07 任务记录整理 | F13 项目记录整理 |
| --- | --- | --- |
| 会话 | 在原工作对话内发送可见整理要求（F06 §3 第 3 步），**不新建会话** | **系统新建**整理对话（OBJ-04、F13-R03） |
| 来源与过程的关系 | 来源对话与生成过程是同一条会话，天然合一 | 来源（任务与工作对话）与生成过程（新会话）分属不同会话，必须显式标记 |
| 主要风险 | 派发消息看起来像用户提问（ADR-001 已记录并接受该代价） | 新会话被误当成工作对话/历史来源，污染工作数量、未记录提示与默认背景 |
| 本 ADR 的作用 | 不引入会话级标记；边界是**不得**为 F06 新建会话或补标记 | 强制会话级标记 + 来源/过程分列 |
| 规则依据 | F06-R01、F06-R04 | OBJ-04、F13-R03、F13-R04 |

F14 的重开更新沿用同一条整理对话（F14-R04「更新继续使用 F13 的……系统整理」），因此标记以 `runId` 支持同一会话内多次操作，而 F14-R01 的「同一成果身份」由结果侧 `provenance.sourceTaskId` 保持不变。

## 7. 可选方案与取舍

**方案 A（推荐）：插件归属表登记整理会话 + 结果侧反向指针**

- 做法：第 3 节的 `consolidation/{sessionId}` 登记 + 草稿/版本上的 `provenance`。
- 优点：结构化、可枚举、与会话标题和消息来源解耦；能直接实现「不计工作对话/数量/未记录提示」和「拒绝绑定」；重启后随项目数据一起恢复（REC-03）。
- 代价：插件需维护一张与宿主会话生命周期同步的归属表；用户在宿主侧删除会话时会留下孤儿标记，必须按 OBJ-09/REC-05 显示「来源已删除」而不是静默清理。

**方案 B：用宿主会话标题或元数据区分（如固定前缀标题）**

- 做法：整理会话统一命名为「系统整理 · <任务>」，靠标题前缀判断。
- 优点：实现最快，界面上天然可见。
- 代价：标题可被用户或模型改写（HOST-02 标题写入语义本身未验证），字符串匹配脆弱；无法承载 `sourceTaskId`/`runId`/`purpose` 等结构化字段；一旦改名即失去区分能力，直接违反 F13-R03。**不推荐**。

**方案 C：只在结果侧记录 `generatedBySessionId`，不登记会话**

- 做法：不标记会话，从项目记录草稿反查生成它的会话。
- 优点：不动会话归属表，改动最小。
- 代价：无法在会话列表、工作数量与未形成记录提示处排除整理对话（这些判断发生在会话层，而 OBJ-04/F13-R03 正要求排除）；取消/失败后没有草稿就没有标记，追溯链断裂。**只作为方案 A 的补充（反向指针）保留，不单独采用。**

## 8. 采用方案与理由

采用**方案 A**，并把方案 C 的 `generatedBySessionId` 作为反向指针一并保留：

1. 只有会话级显式标记能同时满足 OBJ-04 的「不计工作对话/数量/提示」「不允许绑定」与 F13-R03 的归属约束；派生视图 `workspace.sessionIds` 与标题都不具备这个能力。
2. 结构化字段承载了 F13-R04 要求的两个来源（正式任务记录及其版本 vs 生成过程），使展示层分列有据可依。
3. 会话标记 + 结果反指针双向可核对，符合 REC-03「结果未知先核对」与 SAVE-08「保存来源与追溯」的要求。
4. 不需要新的宿主能力：建会话用已验证的 `create({workspaceId})`；过程读取复用三条既有读取通道（尚需在整理会话场景验证，见第 11、12 节）。

## 10. 约束与代价

1. **归属表维护成本**：整理会话标记需要与会话生命周期同步；宿主侧删除会话后的孤儿标记按 OBJ-09 保留说明、按 REC-05 报错不覆盖。
2. **扣除算法的失败保护**：无法读取归属表时不得把整理对话当作工作对话（否则工作数量与未记录提示会错）；显示需核对。
3. **展示层新增区域**：项目成果详情与待确认列表各增加一个「生成过程」线索；F13 §7 允许调整预览布局，但不得因此增加普通确认次数或隐藏失败。
4. **不扩权**：本设计不新增产品功能、不改变固定归属、成对保存、历史隔离与人工修正语义；过程对话不得成为证据、不得进入默认背景、不得作为历史授权。

## 11. 验证证据

**当前为空／待取证**：本记录虽已于 2026-10-20 转「采用」，但**采用依据是用户确认的设计决定，不是工程验证**；本节尚无任何实测证据，未验证不得写为已验证。取证完成后在本节补充证据并按实测/探针/未验证分级标注。

将来按下列办法取证（沿用 ADR-001/ADR-003 的分级写法：实测、探针、未验证分别标注）：

- **单元测试**：`consolidation/{sessionId}` 的写入/读取/重启一致性；`sessionIds` 扣除算法的边界（空表、孤儿标记、跨项目）；绑定路径拒绝。
- **隔离宿主探针**：用 `create({workspaceId})` 建会话并登记标记，核对扣除后的工作对话集合与数量；用 ADR-003 的 `agent/pre-step` 计数办法证明整理对话内容不进入默认背景（恰好一条、只发生 step 1）。
- **集成/手工场景**：跑通 F13-R03 全流程（生成 → 查看过程 → 取消/重试 → 确认），核对只读面板、来源/过程分区、待确认计数与「未形成记录」提示。
- **失败路径**：归属表损坏、会话被宿主侧删除、结果未知重启后核对（REC-03/REC-05）。
