# 功能验收记录模板（verification.md）

> 用法：每个功能在**开始验收**时于 `docs/prd/features/Fxx-slug/verification.md` 创建本文件，按下面的必填字段逐条填写。本模板规定记录格式，不预置任何结果。
> AT 状态与证据口径的权威规则见[验收执行规则](../../engineering/acceptance-execution.md)；进度与验收状态汇总只登记在[交付状态](../../delivery/status.md)。

## 填写规则（必读）

1. **不得预填虚构结果**：未实际执行的行，结论一律写「待执行」，实际结果与证据留空，不写「预期会通过」「应该可以」。
2. **一次记录对应一个提交**：`提交号` 写实际执行时的 commit（全 40 位或至少 7 位短号）；代码或环境变化后重新执行须新建记录或追加章节，不覆盖旧记录。
3. **证据必须可复现**：命令写原文，输出写实际 stdout/stderr 或落盘路径；截图/报告写相对仓库的路径。引用证据不得只写结论。
4. **跨功能未就绪**：依赖功能尚未实现/验收时，结论写「待联合验收」，并注明等待哪个功能与哪个 AT；不得单方面写「通过」。
5. **结论词表**只允许：`通过` / `失败` / `待执行` / `结果需核对`；与[交付状态](../../delivery/status.md)的状态词表一致。
6. **不写产品验收之外的内容**：宿主能力复验、单元测试、探针结果可以列为证据档位，但只有覆盖 AT 场景的证据才能把 AT 标为「通过」（档位定义见[验收执行规则](../../engineering/acceptance-execution.md)）。

## 1. 基本信息（必填）

| 字段 | 内容 |
| --- | --- |
| 功能编号 | Fxx |
| 功能标题 | （来自 feature-catalog.json） |
| 执行日期 | YYYY-MM-DD |
| 提交号 | （实际执行时的 commit，例如 `ed6b151`） |
| 环境 | DSH 版本 / node 版本 / pnpm 版本 / 运行 profile（例如 DSH 44.7.0 nightly、node v24.21.0、pnpm 11.7.0、`--profile web` 隔离宿主） |
| 执行人 / 方式 | （例如：隔离宿主手工场景 / 集成测试 / 探针 + 手工断言） |
| 依赖功能状态 | （各前置功能当前的实现/验收状态，引用交付状态） |

## 2. 验收条件执行记录

每个 AT 一行；同一 AT 多轮执行时分别记录（可加「轮次」列或拆分小节）。前置条件可写在操作步骤内，与 [feature-prd 模板](feature-prd.md) §6 的写法一致。

| AT 编号 | 前置条件 | 操作步骤 | 预期结果 | 实际结果 | 证据（命令原文 + 输出/路径） | 结论 | 归属 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| AT-xxx | （可并入步骤） | | | | | 待执行 | 本功能 / 待联合验收（联合 Fyy） |

- 预期结果必须与 PRD §6 该行的预期一致；实际结果只写观察到的内容。
- 证据示例：`pnpm -r --if-present run test` → 输出粘贴或指向报告文件；手工场景写「操作序列 + 观察到的界面/数据 + 截图路径」。
- 涉及故障注入的执行，必须在该行证据里注明**注入方式与开关名**（规则见[验收执行规则](../../engineering/acceptance-execution.md) 的注入政策）。

## 3. 结论与局限

| 项 | 内容 |
| --- | --- |
| 本功能验收结论 | 待执行 / 通过 / 失败 / 结果需核对（按 AT 汇总；存在未执行或未关闭项时不得写「通过」） |
| 通过项 | （AT 列表） |
| 失败 / 需核对项 | （AT 列表 + 原因） |
| 未执行项 | （AT 列表 + 原因） |
| 跨功能待联合验收 | （AT 列表 + 等待的功能） |
| 局限 | 环境、数据、未验证路径（例如客户端实际渲染未观察、真实 profile 未安装） |
| 与上次记录的差异 | 仅追加场景填写；不覆盖既有记录，不删除失败记录 |
